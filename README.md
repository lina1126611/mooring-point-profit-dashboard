# Mooring Point — 경영지원 대시보드

프로젝트 수주형 엔지니어링 기업을 위한 2단 손익 대시보드.
**Python + Streamlit + SQLite**

> **학습·포트폴리오용 저장소입니다.** 특정 기업의 실제 회계 데이터는 포함하지
> 않습니다. 화면과 문서에 나오는 모든 금액·거래처·현장명은
> `scripts/generate_sample_data.py` 가 생성한 가상값입니다.

---

## 무엇을 푸는가

수주형 엔지니어링 기업의 원가 회계에는 두 가지 공백이 반복해서 생긴다.

1. **일반적인 ERP는 고정비와 변동비를 구분해 주지 않는다.**
   그래서 *"현장에서 돈이 남았는데 최종적으로 왜 안 남았는지"* 를 설명할 수 없다.
2. **설계 인력의 맨데이(투입 인건비)가 원가에 안 잡히는 경우가 많다.**
   그 결과 프로젝트 이익률이 실제보다 과대표시된다.

현장 단위 이익은 보이는데 회사 전체 이익과의 간극이 설명되지 않는다.
이 간극 = **배부되지 않은 고정비 + 계상되지 않은 맨데이 인건비**.

## 핵심 설계 — 2단 손익 구조

```
[1단] 공헌이익 (현장이익)
      = 프로젝트 매출 − 변동비

[2단] 진짜 영업이익
      = 공헌이익 − 배부된 고정비 − 맨데이 인건비
```

- **1단**은 현장이 벌어온 돈. 기존에 보고 있던 숫자.
- **2단**은 회사에 실제로 남는 돈. 안 보이던 숫자.

대시보드는 두 숫자를 **나란히** 놓고, 그 **차이를 항목별로 분해**해서
"왜 안 남았는지"에 답한다 (고정비 배부액 / 맨데이 인건비 / 이자비용).

## 화면

| 페이지 | 내용 |
|---|---|
| **아침 브리핑** | KPI 4종, 현장별 `공헌이익률 vs 진짜이익률` 비교차트, 저수익·적자 경고, 향후 3개월 고정비·이자 |
| **프로젝트 상세** | 손익 폭포차트(매출→변동비→공헌이익→고정비→맨데이→진짜 영업이익), 거래 내역, 맨데이 입력 |
| **설정** | 차입금(등록 즉시 월이자 표시), 월 고정비, 고정비 배부기준, 표준일당 |
| **데이터** | 엑셀 업로드, 분류 수정(일괄 지정 포함), 재분류 |

폭포차트의 맨데이 구간은 색이 아니라 **빗금**으로 구분한다 —
"ERP에 안 잡히던 원가가 여기 있다"가 이 차트의 요점이기 때문이다.

## 실행

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt

python scripts/generate_sample_data.py   # 샘플 엑셀 생성 (data/sample/)
python scripts/load_sample_data.py       # db/mooring.db 적재 + 품질 점검
streamlit run app.py                     # http://localhost:8501
pytest
```

## 구조

```
app.py              Streamlit 진입점 (얇은 UI 레이어)
src/
  db.py             SQLite 연결 + 스키마 초기화
  rules.py          분류 규칙 (컬럼 별칭 / 계정 키워드 / 원가행태 매핑)
  ingest.py         엑셀 로딩·정규화·DB 적재
  classify.py       계정과목 → 원가행태(변동/고정/해당없음) 분류
  profit.py         2단 손익 엔진
  finance.py        이자비용, 고정비 배부
  masters.py        차입금·고정비·맨데이·표준일당 CRUD
  report.py         리포트 조립 (요약표, 차트용 데이터)
scripts/            샘플 생성 · 적재 · 검산
db/schema.sql       SQLite 스키마
tests/              pytest (220 케이스)
```

금액 계산식은 전부 `src/` 안에 두고 `app.py` 는 얇게 유지한다.
UI 코드에 계산식을 넣으면 테스트가 불가능해지기 때문이다.

## 설계 원칙

**모든 금액 계산은 pytest로 검증한다.** 이 프로젝트의 최우선 규칙이다.

- 손익 항등식을 회귀 테스트로 고정:
  `공헌이익 − 배부고정비 − 맨데이인건비 = 진짜 영업이익`
- 배부 로직은 **배부 총액이 원본 총액과 일치**하는지 검증 (반올림 잔차 포함)
- 통화는 원(KRW) 정수 저장. 부동소수점 누적 오차를 피한다.

**모르면 모른다고 남긴다.** 규칙에 안 걸리는 거래는 `미분류` 로 두고
변동비·고정비 어느 쪽에도 넣지 않는다. 억지로 끼워 맞추면 손익이 조용히
틀어지기 때문이다. 대신 미분류 총액을 UI에 항상 노출한다.

같은 이유로 **현장 미귀속 변동비**(변동으로 분류됐지만 `project_id` 가 비어
있어 어느 현장 원가에도 안 잡히는 금액)도 별도로 집계해 노출한다.
분류가 돼 있어서 미분류보다 발견이 늦은 누락이다.
